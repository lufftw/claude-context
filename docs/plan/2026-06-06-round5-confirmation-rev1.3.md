## Any residual edits to add to the rev1.2 patch-list before coding (exact, minimal)

**Add-1 (new patch-list item 6b) — make `processChunkBuffer` the explicit `BatchOutcome`-returning, tuple-forwarding intermediary.** This is the load-bearing omission: the real call graph is three levels (`processFileList` → `processChunkBuffer` at 957/1012 → `processChunkBatch` at 1053), and edit 8 awaits `processChunkBuffer`, not `processChunkBatch`.
- `context.ts:1040` — change signature to `private async processChunkBuffer(chunkBuffer: Array<{ chunk: CodeChunk; codebasePath: string; relativePath: string }>): Promise<BatchOutcome>`.
- `context.ts:1044` — remove `const chunks = chunkBuffer.map(item => item.chunk)`; forward the full tuple array to `processChunkBatch` so `relativePath` (edit 4) survives to `BatchOutcome.perFile`. Update edit 6's `processChunkBatch` signature to accept the tuple array. `return` the `BatchOutcome` up to the counter.
- Without this, edit 8's `const r: BatchOutcome = await this.processChunkBuffer(...)` references a producer no edit creates, and edit 4's `relativePath` field has no consumer (it is dropped at 1044 before `processChunkBatch` is reached; today `relativePath` is recomputed *inside* `processChunkBatch` at 1073/1109 from `chunk.metadata.filePath`). Decide one source-of-truth: forward the tuple (preferred — keeps the buffer key authoritative).

**Add-2 (amend item 15 / Layer-5) — pre-Phase-3, `absent + milvusSaysSame` must `deleteByFilter(relativePath)` before re-embed, NOT plain idempotent insert.** The kill-resume lens is correct: the killed-in-flight file is `absent` (not `complete:false`), so the spec's "absent ⇒ avoid destructive pre-delete" routes it to a plain re-insert that, under the non-upsert path (insert returns void, discards `MutationResult`, 345/365), re-inserts chunks 1-4 under identical deterministic PKs → duplicate physical rows → non-deterministic `fileHash` in `loadExistingFileHashes` (dedup at 847 keeps first-in-iterator). Amend item 15 to a three-way branch:
- `complete:false` → `deleteByFilter` + re-embed (unchanged).
- `absent + milvusSaysSame`, **Phase-3 active (upsert available)** → upsert, no pre-delete (as written).
- `absent + milvusSaysSame`, **pre-Phase-3 (insert only)** → `deleteByFilter(relativePath)` + re-embed.
- Rationale: the file is not being skipped (it re-embeds in full from live content this run), so the pre-delete loses no correctness and cannot lose chunks; it is the only pre-upsert way to avoid the duplicate-PK non-determinism the Attack-3 closure depends on. "Avoid destructive pre-delete" is correct *only once upsert exists*.

**Add-3 (amend item 10 / Layer-3 3c) — fire `onFileComplete` at flush time keyed off `BatchOutcome.perFile`, not at the file-loop boundary (991).** With default `EMBEDDING_BATCH_SIZE=100` and cross-file buffering, a just-finished file's chunks usually sit unflushed when control reaches 991, so a boundary-fired `onFileComplete` reads `inserted:0 → complete:false` for nearly every file (defeating the ledger's main value) or reads a tally not yet produced. Amend item 10: after each `mergeFileProgress(fileProgress, r.perFile)`, for every `rp ∈ r.perFile` whose accumulated `produced === fileChunkTotals.get(rp) && produced === inserted`, fire `onFileComplete(rp, …)` exactly once, deduped via a `firedComplete: Set<string>`. The `incompleteByLimit` tag at the CHUNK_LIMIT break (984-988) still forces the in-flight file to `complete:false` regardless.

**Add-3b (clarify item 8) — preserve the unconditional `chunkBuffer = []` reset.** Item 8 says "replace 955-980"; lines 978-980 are the `finally { chunkBuffer = [] }`. State explicitly: after the now-throwless `processChunkBuffer` returns, keep an unconditional `chunkBuffer = []` outside any catch. A literal applier that deletes the whole 955-980 block would drop the reset and the buffer would grow unbounded / re-embed. One line; flagged so it is not lost. (Sub-item of Add-1's region; not a separate edit.)

No other residual. The `attack1-closed` and `rogue-guard-preserved` "notes" are design-intent guards already in-spec (item 5: total from splitter length; item 16a: route through real consumer) and require no code change — they become **acceptance assertions** in the item-16 tests.
