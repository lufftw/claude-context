## Composed seam resolution — the rev1.2 design for Tasks 1.4/1.5/1.6/2.3 as ONE coherent mechanism

The five layers below form a single producer→consumer→reducer→callback→ledger pipeline. Every layer's contract is stated so the next layer can rely on it. Exact signatures and return types named throughout.

### Layer 0 — provider reply seam (Task 1.4 prerequisite, was P40; now Tier-1)

`rabbitmq-embedding.ts`, inserted **before** the `pending.resolve(vectors[0])` at line 197:

```ts
const v = vectors[0];
let sumSq = 0;
for (let k = 0; k < v.length; k++) sumSq += v[k] * v[k];   // loop-sum, NEVER Math.hypot(...v) — 4096-arg spread throws RangeError
const norm = Math.sqrt(sumSq);
if (v.length !== this.config.dimension || !(norm > 0.5 && norm < 2.0)) {
    pending.reject(Object.assign(
        new Error(`bad embedding: len=${v.length} expected=${this.config.dimension} norm=${norm.toFixed(3)}`),
        { embedReason: 'bad-dimension' as EmbedReason }
    ));
    return;
}
pending.resolve(v);
```

This is what makes a 1536-dim `success:true` rogue reply become a *failure with a REAL reason* instead of resolving clean. **Without this layer, P31 has nothing to classify** (verified: line 197 today resolves any non-empty array-of-arrays). The `length !== dimension` check is mandatory and independent of the norm band — a *normalized* 1536-dim vector has norm ≈ 1.0 and would pass the band alone.

### Layer 1 — `embedBatchPartial` (Task 1.4 core; was P18)

New method on `RabbitMQEmbedding` (and a base-class default for other providers that wraps `embedBatch` in one all-or-nothing result). Exact return type, added to `base-embedding.ts`:

```ts
export type EmbedReason =
    | 'worker-error' | 'bad-dimension' | 'malformed' | 'insert-error'   // REAL class
    | 'timeout' | 'no-consumer' | 'connection-lost';                    // WAIT class

export const REAL_REASONS: ReadonlySet<EmbedReason> =
    new Set(['worker-error', 'bad-dimension', 'malformed', 'insert-error']);

export interface EmbedItemResult {
    index: number;                       // original position in the input array
    ok: boolean;
    vector?: number[];                   // present iff ok
    dimension?: number;                  // actual length of vector (NOT config-stamped)
    reason?: EmbedReason;                // present iff !ok
}

// returns one result per input chunk, index-aligned; NEVER throws for per-slot faults
embedBatchPartial(chunks: string[]): Promise<EmbedItemResult[]>;
```

`embedBatchPartial` routes each slot through `sendOneWithRetry` (Task 1.3): WAIT-class reasons (`timeout`/`no-consumer`/`connection-lost`) are retried to exhaustion; REAL-class reasons (`worker-error`/`bad-dimension`/`malformed`) are not retried, settled immediately as `{ok:false, reason}`. `dimension` is the **actual** `v.length`, never the config value — Attack 2 showed config-stamping hides the rogue.

### Layer 2 — `processChunkBatch` per-file `failedIndices` + REAL/WAIT partition (Task 1.5)

`context.ts:1059`. Changes from the current all-or-nothing `embedBatch` call (line 1064):

```ts
interface BatchOutcome {
    perFile: Map<string, { produced: number; inserted: number }>;  // keyed by relativePath
    realFailures: number;     // count of slots whose reason ∈ REAL_REASONS
    waitFailures: number;     // count of slots whose reason ∈ WAIT (after retry exhaustion)
    successes: number;        // count of slots inserted
}

private async processChunkBatch(
    chunkBuffer: Array<{ chunk: CodeChunk; codebasePath: string; relativePath: string }>,  // P33: relativePath threaded
    isHybrid?: boolean
): Promise<BatchOutcome>
```

Mechanism:
1. `const results = await this.embedding.embedBatchPartial(chunkContents);`
2. **Second-seam guard (was P41):** for each `ok:true` slot, re-check `results[k].dimension === this.embedding.getDimension()` with the same loop-sum norm band. A slot that fails here is downgraded to `{ok:false, reason:'bad-dimension'}`. This is defense-in-depth for non-RabbitMQ providers and any Layer-0 regression. Loop-sum norm, never spread.
3. Build `documents` from `ok:true` slots only, using **paired-tuple compaction** (was P42): zip `(originalChunk, result)` so a dropped slot never index-shifts the survivors onto the wrong chunk.
4. `const mut = await this.vectorDatabase.insert(...)` / `insertHybrid(...)` — **result-checked** (was P32): if `mut.error_code !== 'Success'` OR `mut.insert_cnt !== documents.length`, tag every slot in this insert as `{ok:false, reason:'insert-error'}` (REAL) and do NOT count them as `inserted`. This closes the "ledger seals complete on a zero/partial-row insert" path (verified: `milvus-vectordb.ts` discards the `MutationResult` today).
5. Tally per file: each slot increments `perFile.get(relativePath).produced`; each *confirmed-inserted* slot increments `.inserted`. Increment `realFailures`/`waitFailures`/`successes` accordingly.
6. **Return `BatchOutcome`. Throw ONLY on an abort-worthy infrastructure error** (e.g. the vectordb connection itself is gone), never for per-slot faults.

### Layer 3 — `processFileList` per-file tally + three-way counter + `complete = produced === chunks.length` (Task 1.6 + the Attack-1 fix)

`context.ts:894-1035`. Three changes:

**(3a) Buffer carries `relativePath` and the splitter's total chunk count is recorded per file.** At line 935 after `split`, record `fileChunkTotals.set(relativePath, chunks.length)`. At line 951: `chunkBuffer.push({ chunk, codebasePath, relativePath })`. Maintain `const fileProgress = new Map<string, {produced:number; inserted:number}>()` accumulated from each `BatchOutcome.perFile`.

**(3b) Three-way counter replaces the binary throw/reset at lines 955-980:**

```ts
const r: BatchOutcome = await this.processChunkBuffer(chunkBuffer);   // returns partition; throws only on infra abort
mergeFileProgress(fileProgress, r.perFile);
if (r.realFailures > 0) {
    consecutiveBatchErrors++;
    if (consecutiveBatchErrors >= MAX_CONSECUTIVE_BATCH_ERRORS) {
        throw new Error(`Aborting indexing: ${MAX_CONSECUTIVE_BATCH_ERRORS} consecutive REAL-class batch failures...`);
    }
} else if (r.successes > 0) {
    consecutiveBatchErrors = 0;                  // reset ONLY on a clean, productive batch

// pure WAIT-class (realFailures===0 && successes===0): leave counter UNCHANGED — genuinely neutral
```

This is the fix for **Break #1**: the old `=0`-on-any-return semantics let an alternating rogue/timeout attack reset accumulated strikes (REAL, wait→reset, REAL, wait→reset… never reaches 3). Neutrality cannot be decided from a void return + try/catch — it requires the `BatchOutcome` partition. **The identical three-way branch must be applied to the final-batch flush at lines 1008-1020**, which today re-throws unconditionally; otherwise a trailing rogue chunk in the last sub-batch bypasses the classifier.

**(3c) The Attack-1 fix — `complete` is gated on the splitter total, not on the running tally.** When a file's last chunk has flushed (detected at the next file boundary or at end-of-run), fire:

```ts
const fp = fileProgress.get(relativePath);
const total = fileChunkTotals.get(relativePath);
const complete = !!fp && fp.produced === fp.inserted && fp.produced === total;   // ← `=== total`, NOT just produced===inserted
onFileComplete?.(relativePath, { complete, fileHash, chunkCount: fp?.inserted ?? 0 });
```

Crucially, **at the `CHUNK_LIMIT` break (lines 984-988) the in-flight file is tagged `incompleteByLimit`** so its `onFileComplete` fires `complete:false` regardless of count coincidence. `produced === total` makes the chunk-limit-truncated file (produced 4, total 10) fail the completeness test even though `produced === inserted`. This is the line that turns NO-GO into GO on the blocking trace.

## Duplicate-PK impact on Phase 3 (definite call)

**Upsert is sufficient for forward correctness. Compaction is REQUIRED for correctness of the read-back path (`loadExistingFileHashes`/the resume ledger reconciliation), not merely hygiene — but it is a ONE-TIME remediation, not a per-run step.** Here is the call with reasoning.

**Why upsert is sufficient going forward.** `generateId` (`context.ts:1181`) is `chunk_<sha256(relativePath:startLine:endLine:content)>` — deterministic and content-derived. Milvus `upsert` on a VarChar PK is delete-then-insert-by-PK atomically; re-embedding identical content yields the identical PK, so upsert collapses to one physical row. Phase 3 replacing the `deleteByFilter(relativePath)` + `insert` pair with `upsert` (a) removes the kill window between delete and insert (the crash-safety win), and (b) **stops manufacturing new duplicates**. From the first all-upsert run forward, no new PK duplication occurs. The live ground truth (claude_context_own 2176 physical / 800 distinct; event_shared 585312 / 162703) is the accumulated debt of the historical `insert`-without-uniqueness path — upsert prevents *growth* of that debt.

**Why upsert alone is NOT sufficient for correctness, and compaction IS required (once).** Two reasons, both correctness, not hygiene:

1. **Orphan-on-shrink.** `generateId` keys on `startLine:endLine:content`. When a file is edited so a chunk's boundaries shift (a chunk that was lines 40-60 becomes 38-57), the *new* chunk gets a *new* PK; the *old* PK is not overwritten by upsert (upsert only touches PKs present in the write set). The old row is orphaned. Phase 3 must therefore **retain a `deleteByFilter(relativePath)` before the per-file upsert batch** (or use range-delete by relativePath then upsert) to evict boundary-orphaned PKs. Pure upsert without the relativePath sweep leaks stale chunks that pollute search results — a correctness bug, not hygiene.

2. **The duplicate rows already in the collection corrupt the resume ledger's read-back.** `loadExistingFileHashes` (`context.ts:825-858`) dedups by `relativePath` keeping one row's `fileHash`. With duplicate PKs carrying *different* `fileHash` values (an old chunk-1 from indexing run A and a re-inserted chunk-1 from run B both physically present), `queryAll` returns both; the dedup loop (`context.ts:845-852`) keeps whichever arrives first in iterator order — **non-deterministic which `fileHash` wins**. If the stale one wins, P30's `existingHash === fileHash` is wrong and a genuinely-changed file is mis-skipped or a genuinely-unchanged file is needlessly re-embedded. The existing physical duplicates can therefore make the ledger read non-deterministic. **This requires a one-time compaction/dedup pass** (delete-all-then-reindex per collection, or a PK-dedup sweep keeping the newest `lastUpdated`) before the Phase-3 ledger logic can be trusted on the *existing* dup-laden collections.

**Definite call:**
- **Phase 3 = upsert + retained per-file `deleteByFilter(relativePath)` sweep for orphan-on-shrink.** Upsert for the kill window; the sweep for boundary orphans. Both are correctness.
- **A one-time per-collection compaction/dedup is REQUIRED before the resume ledger is trustworthy on existing collections** (because pre-existing duplicate PKs with divergent `fileHash` make `loadExistingFileHashes` non-deterministic). This is a migration step, not a recurring one.
- **Recurring Milvus segment compaction is hygiene** (reclaims space from upsert's delete-tombstones) and is NOT required for correctness — Milvus auto-compacts.

So: upsert sufficient for *new* writes; orphan-sweep required for *changed* files; one-time dedup required for *existing* dup-laden collections before the ledger read is sound.

## Residual risks accepted

1. **Default `EMBEDDING_BATCH_SIZE=100` + cross-file buffer means most small files never flush "mid-file."** The kill-mid-file scenario only bites on batch-boundary straddles or small batch sizes. The rev1.2 design is correct for both, but the *common* case rarely exercises the resume ledger's partial-file path — so the ledger's main value is "don't re-index the whole 162k-chunk codebase on every crash," not fine-grained mid-file resume. Accepted.

2. **`generateId` boundary-sensitivity means any whitespace/format edit that shifts chunk boundaries re-embeds the whole file**, even if 90% of content is unchanged. This is pre-existing upstream behavior, not introduced by rev1.2. Accepted; not in scope.

3. **The shared multi-user snapshot under `CLAUDE_CONTEXT_HOME` field-merge (Layer-4 P6)** reduces but does not eliminate cross-session ledger races — two sessions indexing the *same* codebase path concurrently can still interleave `files` writes. The lockfile (`proper-lockfile`, per the snapshot bugfix doc) serializes the *write*, and field-merge makes interleaving non-destructive, but last-writer-wins on a *specific* `files[rp]` entry remains. Accepted: concurrent same-path indexing is not a supported workflow.

4. **Result-checked insert (P32) trusts Milvus `insert_cnt`.** A Milvus partial-success that *reports* full `insert_cnt` but silently drops rows server-side would still seal `complete:true`. No client-side defense exists without a read-back verify per batch (too expensive). Accepted as a Milvus-trust boundary.

5. **Pre-existing ~1,400 stale `140.115.54.62` references and the historical duplicate-PK debt** are not remediated by this work. Accepted residual (tracked elsewhere).
